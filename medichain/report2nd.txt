1) CURRENT PRODUCT SHAPE FROM CODE
================================================================================

The project is a Django + DRF multi-role healthcare platform with two parallel interaction styles:
1. REST API layer for programmatic clients under /api/v1/ and /api/v1/patient/
2. Server-rendered web portal layer for hospital admin/staff and patients using Django templates

The implemented role set in code:
- Hospital admin
- Doctor
- Nurse
- Technician
- Patient

Core implemented domains:
- Hospital onboarding and account activation
- OTP-based email verification for hospital account bootstrap
- Role-aware auth and authorization via JWT (API) and session decorators (web)
- Staff lifecycle management (doctor/nurse/technician)
- Patient lifecycle management with encrypted government ID storage
- Lab management and lab request workflow
- Dynamic lab custom fields with per-role field ownership
- Technician record creation/edit with immutable version timeline
- Doctor reassessment and versioned record updates
- Nurse queue workflow and doctor-finalized narrative record workflow
- Patient portal with profile-completion gate and record access
- Dynamic per-hospital data storage strategy for local record tables

2) ARCHITECTURE AND DATA LAYER IMPLEMENTATION
================================================================================

2.1 Database topology in code
- Default/shared MySQL database stores common entities:
  - hospitals, hospital_users, patients, assignments, labs, lab requests, metadata, queue
- Hospital-local dynamic databases store record payload tables (generated per lab):
  - lab_record_<labidprefix>
  - lab_record_version_<labidprefix>

Relevant code:
- hospitals/db_router.py
- hospitals/hospital_db.py
- hospitals/lab_table_manager.py
- hospitals/middleware.py
- medichain/settings.py

2.2 Dynamic DB registration and provisioning
- register_db(hospital_id): creates runtime DB alias like hospital_<uuidprefix>
- create_hospital_database(hospital_id):
  - creates physical MySQL DB medichain_h_<uuidprefix>
  - runs migrations for hospital_local app on that DB
- ensure_db_exists(hospital_id):
  - verifies connection
  - auto-provisions DB on MySQL 1049 unknown database error

2.3 Router behavior
- hospital_local app reads/writes go to current hospital alias from thread-local context
- non-hospital_local models stay on default DB
- migration routing:
  - hospital_local migrates only on hospital_* aliases
  - shared apps migrate on default only

2.4 Thread-local context
- set_hospital_db, get_hospital_db, clear_hospital_db
- middleware HospitalDBContextMiddleware sets context from request session hospital_id
- context is always cleared in finally block to avoid leakage

2.5 Dynamic table strategy for lab records
- lab_table_manager builds SQL schema per lab
- base columns include:
  - identity and linkage fields
  - diagnosis/treatment/notes/chest_pain_type
  - technician fields age/gender
  - version/hash/timestamps
- custom lab fields are appended as columns
- supported custom field types:
  - text, textarea, number, integer, decimal, date, choice, boolean

2.6 Versioning approach
- Current row table keeps latest state (is_latest=1)
- Version table appends immutable snapshots with:
  - version_number
  - changed_by_id
  - change_reason
  - snapshot columns
- fetch_record_history returns ordered version timeline

3) SECURITY, AUTH, IDENTITY, DATA PROTECTION
================================================================================

3.1 JWT implementation
- Custom authentication class: MediChainJWTAuthentication
- Does not bind to Django User model
- Returns AnonymousUser and stores custom payload in request.user_payload
- Payload supports hospital admin/staff/patient claims

3.2 JWT generation
- token_utils.get_tokens_for_payload writes custom claims into both refresh and access tokens
- Used across hospital admin login, staff login, and patient login API flows

3.3 API permission classes
- IsHospitalAdmin: user_type == hospital_admin
- IsDoctor: staff_role == doctor
- IsNurse: staff_role == nurse
- IsTechnician: staff_role == technician
- IsStaff exists for user_type == staff

3.4 Session-based web auth guards
- hospital_admin_required
- doctor_required
- nurse_required
- technician_required
- patient_required (in patient app)

3.5 Password security
- Passwords are hashed via Django make_password/check_password
- Shared helper update_password_with_verification enforces:
  - current password validation
  - minimum length
  - new/confirm match

3.6 Government ID protection
- Plain gov ID is encrypted at rest via Fernet
- Duplicate detection uses SHA-256 hash of gov_id_type + gov_id_number
- UI/API expose masked values, not plaintext

3.7 Record integrity checks
- Record payload hashes are generated and persisted
- Finalized nurse-doctor flow records include stored hash + computed hash verification in detail bundle

5) HOSPITAL ADMIN WORKFLOW - IMPLEMENTATION DETAILS
================================================================================

5.1 Registration and OTP
- service_register_hospital validates:
  - hospital_name required
  - email format and uniqueness
  - India phone format and uniqueness
  - password rules
- Deletes stale unverified records for same email/phone before new registration
- Generates OTP with 10 min expiry
- Creates hospital row
- Provisions dedicated hospital DB immediately
- Sends verification email

5.2 OTP verification and resend
- service_verify_otp checks existence, expiry, and correctness
- On success sets email_verified true and clears OTP fields
- service_resend_otp rotates OTP and expiry then sends email

5.3 Login behavior
- service_login checks Hospital table first (admin login path)
- Enforces email verification and status checks
- Falls back to HospitalUser for staff login
- Distinguishes error classes for API status mapping in api_views

5.4 Activation progression
- check_and_activate_without_session triggers active status when:
  - license locked
  - address/city/state/country present
  - current status pending

5.5 Admin profile locks
- Name update allowed once then name_locked true
- License update allowed once then license_locked true
- Address remains editable

5.6 Admin dashboards
- Hospital dashboard provides staff/patient counters
- record/report counters are currently placeholders in both API and web views

9) TECHNICIAN RECORD WORKFLOW - IMPLEMENTATION DETAILS

9.1 Queue retrieval

9.6 Record detail payload

10) DOCTOR REASSESSMENT AND CLINICAL UPDATE FLOW
================================================================================

10.1 Reassessment entry

10.2 Queue behavior toggle

11) NURSE QUEUE TO FINALIZED RECORD FLOW
================================================================================

11.1 Queue item creation
- Doctors create queue items with:
  - title, primary diagnosis, key instruction
  - optional doctor note
  - handwritten file

11.2 Nurse queue execution
- Queue states: pending, in_progress, completed
- Nurse opening pending item auto-picks item and marks in_progress
- Completion requires full clinical set (bp, pulse, temp, spo2, sugar, tests, observation, treatment, meds)
- Saves nurse data and completion timestamp

11.3 Doctor approval queue
- Pulls completed but not finalized items
- Finalization requires doctor final notes
- Finalization stores:
  - consolidated payload
  - finalized record id
  - payload hash
  - finalized_by and finalized_at

11.4 Finalized medical record access service
- service_get_finalized_medical_record_detail checks role-specific ownership:
  - doctor must match hospital and doctor_id
  - nurse must match hospital and picked_by
  - patient must match patient_id
- Returns record bundle with hash verification and one-version timeline
- Includes patient identity display from decrypted gov ID suffix when available

19.5 Profile completion gate for patient access

A) EXACT MODEL FIELDS FOR NEW MODULES (NAME, TYPE, PURPOSE)
--------------------------------------------------------------------------------

A1) Lab model (hospitals/models.py)
1. id: UUIDField(pk, default uuid4, editable=False)
Purpose: unique lab identity.
2. hospital: ForeignKey(Hospital, CASCADE, related_name='labs')
Purpose: owner hospital for this lab.
3. lab_type: CharField(max_length=50, choices=LAB_TYPE_CHOICES)
Purpose: logical lab category (ckd/pathology/radiology/etc).
4. name: CharField(max_length=255)
Purpose: display name of lab.
5. custom_field_schema: JSONField(default=list, blank=True)
Purpose: dynamic per-lab field schema definition.
6. is_active: BooleanField(default=True)
Purpose: soft-archive toggle for lab lifecycle.
7. created_at: DateTimeField(auto_now_add=True)
Purpose: creation timestamp.

Model constraints:
- unique_together = (hospital, lab_type)
- ordering = [name]

A2) LabAssignment model
1. id: UUIDField(pk, default uuid4)
Purpose: assignment row identity.
2. lab: ForeignKey(Lab, CASCADE, related_name='assignments')
Purpose: target lab.
3. technician: ForeignKey(HospitalUser, CASCADE, related_name='lab_assignments')
Purpose: assigned technician.
4. assigned_at: DateTimeField(auto_now_add=True)
Purpose: assignment timestamp.

Constraints:
- unique_together = (lab, technician)
- ordering = [-assigned_at]

A3) LabRequest model
1. id: UUIDField(pk, default uuid4)
Purpose: request identity.
2. patient: ForeignKey(Patient, CASCADE, related_name='lab_requests')
Purpose: patient under investigation.
3. lab: ForeignKey(Lab, CASCADE, related_name='requests')
Purpose: target lab.
4. requested_by: ForeignKey(HospitalUser, CASCADE, related_name='requested_lab_requests')
Purpose: doctor who created request.
5. status: CharField(max_length=20, choices pending/in_progress/completed, default pending)
Purpose: queue state.
6. created_at: DateTimeField(auto_now_add=True)
Purpose: request creation time.
7. completed_at: DateTimeField(null=True, blank=True)
Purpose: completion time.
8. chest_pain_type: CharField(max_length=20, choices typical/atypical/non_anginal/asymptomatic)
Purpose: clinical classification.
9. diagnosis: TextField()
Purpose: doctor diagnosis.
10. treatment_plan: TextField()
Purpose: doctor treatment plan.
